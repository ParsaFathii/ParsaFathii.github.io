STATION 01 THE OPERATOR PROFILE

Software that survives contact with reality.

I build software that has to work when it is raining, offline, and three metres underground.

My main work is SPERLUS — a sewer-inspection operations platform I designed and develop end to end: a field desktop program for CCTV pipe inspection, a role-based web control center, and the backend service that keeps them in sync. It is delivered to a real client, deployed on production infrastructure, and has been iterated through dozens of client-driven releases — the desktop software is currently at version 15.14.

Before and alongside that, my background is in automotive electrical systems and ECU programming, which is where the interest in low-level, deterministic, fail-safe software comes from. That thread runs through everything: CAN-bus tooling, a real-time scheduling laboratory, C++ engines with zero-warning policies.

I care about honest engineering: every number an interface shows comes from real data, synthetic data is labelled as synthetic, tests are deterministic, and each public repository documents its own limitations. The work is meant to be inspected — like everything else on this survey.

  • P-01

    Determinism first

    Same input, same result — every time. From discrete-event simulation to field sync, reproducibility is a feature, not an afterthought.

  • P-02

    Evidence over claims

    No metric without a source, no screenshot of a system that does not run. Benchmarks keep their raw observations and their caveats.

  • P-03

    Field-grade reliability

    Offline queues, resumable chunked uploads, idempotent retries, verified self-updates. The field has no patience for "try again later".

  • P-04

    Document like a survey

    Bilingual docs (EN/FA), architecture specs written before code, CI on every public repo, and limitations stated in plain text.

STATION 02 FLAGSHIP OPERATION CASE STUDY

SPERLUS

An industrial sewer-inspection and operations-management platform — desktop field software, a web control center and a central service, built for a real client and running in production.

THE SURVEY PROBLEM

Sewer networks are inspected by dragging CCTV cameras from manhole to manhole. Every defect must be coded to standard (WRC / EN), measured by distance down the pipe, compiled into reports, and then managed as contracts, work orders, teams and invoices. Field crews work underground and offline; the office needs live control. Most toolchains handle one slice of that — SPERLUS integrates the whole operation.

ENGINEERING DECISIONS — RECORDED
  1. D-01

    Modular monolith, not microservices

    One deployable service with hard module boundaries (11 modules, layered router → service → repository). A two-person operation should not operate a distributed system before it needs one.

  2. D-02

    Offline-first, idempotent sync

    The field app commits locally first, then uploads with client-UUID idempotency keys; retries never duplicate a record. Media uploads in resumable 1 MB chunks with checksums; conflicts surface as an explicit state in the UI.

  3. D-03

    Access control as data, not code

    Permissions are atomic and database-managed; roles are sets of permissions; scope is a hierarchy (company → region → contract → project → work order). Explicit DENY overrides GRANT, and every grant and denial is audited.

  4. D-04

    Design before build

    The target architecture — stack, schema, state machines, API surface, mandatory test matrix — was written as a specification document before implementation, and the build followed it section by section.

ByteVault

Local-first encrypted password & secrets manager

No account, no cloud, no telemetry. A single C++20 core implements the vault format — Argon2id key derivation, XChaCha20-Poly1305 encryption through libsodium — and four clients (Flutter desktop, Android, Python CLI, loopback web) bind to that same core through one C ABI.

STATION 04 VISION & RESEARCH AI · CV

Machine vision, measured honestly.

My computer-vision work is classical first: a full license-plate recognition pipeline for Iranian plates — detection, perspective rectification, contour segmentation, grammar-constrained template OCR, tracking — built with OpenCV and benchmarked with its caveats stated in writing. At the other end, EdgeVision is a real-time analytics platform where a C++20 engine tracks objects and raises geometric events, and where swapping the built-in detector for an ONNX model is an architecture slot, not a rewrite.

Where machine learning appears in my systems, it earns its place narrowly: Isolation-Forest and EWMA baselines for anomaly detection, evaluated on labelled datasets and reproducible runs — not bolted-on magic.

The pattern I keep building is AI features that know their place: assistants that are optional, advisory-only, grounded strictly in recorded evidence, schema-validated, and rejected if they cite things that do not exist. The platform must work with every one of them switched off.
